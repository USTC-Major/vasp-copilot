## 1. 用户目标与交付结果

用户希望直接双击软件根目录的 `VASP-Copilot.exe` 使用程序，不再区分 CMD、普通 EXE、完整功能模式等不同用户入口。已有安装目录、手动 Python 路径等启动设置应可靠保存，退出再打开后恢复。

本任务同时解决三件事：

1. **单一入口**：发布包根目录提供唯一面向用户的 `VASP-Copilot.exe`；新包不再提供原来的 CMD 用户启动入口。
2. **入口行为统一**：默认承接现有完整模式的自动 Python 检测、专用依赖环境准备、自动端口及真实功能入口，不因启动方式切换配置或业务空间。
3. **设置可靠持久化**：定位保存旧值/空值问题，补齐保存失败提示、写后核验、读取错误处理与必要的旧配置兼容。

“单 EXE 入口”指用户只需认一个入口，**不是单文件免环境程序**。仍需完整解压资源、前后端和运行组件，仍沿用已有 Python、.NET Framework 4.8、WebView2 Runtime 要求。

## 2. 调查事实：哪些已证实，哪些仍待定位

### 2.1 已确认：CMD 与直接 EXE 读取不同设置

v0.4.1 的 `启动完整功能.cmd` 调用 `desktop/dist/VASP-Copilot-Desktop-V3.exe --full-features`。直接双击该 EXE 不带参数，`desktop/DesktopApp.cs` 会选择另一种模式。

| 入口 | 模式 | 启动设置文件 | 自动准备项目依赖 |
|---|---|---|---|
| CMD | full-features | `%LOCALAPPDATA%/VASP-Copilot/desktop-v040-full/preferences.json` | 是 |
| 直接 EXE | normal | `%LOCALAPPDATA%/VASP-Copilot/desktop-v3/preferences.json` | 否 |

两种模式的单实例标识也不同。因此，从一个入口切到另一个入口，可能看到空设置或另一套旧值，并可能启动不同实例。这是已确认的实现缺陷。

### 2.2 用户现场：同一入口重开也恢复旧值/空值

用户在**另一台电脑**确认：

- 同一入口退出重开也会出现问题，不仅是入口交叉使用。
- 涉及安装目录和手动 Python 路径，不只是 AI 勾选或自动检测后的空输入框。
- 按 CMD 入口保存后查看 `desktop-v040-full/preferences.json`，文件仍为旧值或空值。
- 尚未确认新值是否写进 `desktop-v3`、`launcher` 或其他用户上下文中的配置目录。

这将问题收敛到“预期文件未更新”，但**尚不能唯一确定**是保存失败、实际写入另一个目录、旧实例接收启动，还是其他现场因素。不得把其中任何一种直接写成已证实根因，也不得仅凭移动 EXE 宣布整个问题已修好。

### 2.3 本机已验证的情况与代码缺口

- 使用已发布 EXE 中的真实配置类，在独立合成目录保存中文路径，再用新进程读取，恢复成功。
- 使用已发布的真实启动设置表单，自动触发“保存并启动”，随后另进程读取，新值恢复成功；此检查未启动业务服务、未更改用户配置。
- 生产式“先设置状态目录，再调用 Load”的隔离探针在本机恢复正常；静态初始化时序不能作为已确认根因。
- `LauncherPreferences.Load()` 捕获所有读取/反序列化异常后直接返回默认空设置，没有区分首次使用、损坏、占用或权限问题。
- 保存使用固定 `preferences.json.tmp` 加 `File.Replace`/`File.Move`，缺少明确的用户级失败反馈与写后核验；目前不能据此认定现场一定发生了替换失败。
- 现有 CI 虽覆盖控制器和配置读写，仍缺少发布包真实入口的交叉启动及完整设置闭环验收。

本机成功不代表用户另一台设备已通过。开发回执必须将“已修复并复现验证”与“现场原因尚未取证、已增强防护”分开写。

## 3. 实现合同

### 3.1 根目录 EXE 与依赖定位

目标包结构示意：

```text
VASP-Copilot/
├─ VASP-Copilot.exe          # 唯一用户入口
├─ VASP-Copilot.exe.config
├─ backend/
├─ frontend/
├─ launcher/
└─ desktop/                 # 开发、运行资源等内部文件
```

此图不是要求所有 DLL 都藏进 desktop。首选风险较低的布局：在需要时将 WebView2 托管 DLL、`WebView2Loader.dll` 和许可证放在 EXE 相邻位置；若改为子目录，必须验证托管与原生依赖解析，不能只移动 EXE 或只设置托管 probing。

要求：

- 发布包根目录包含实际可运行的 `VASP-Copilot.exe`，不通过另一个可见启动器转调旧用户 EXE。
- 内部构建暂存位置可保留 `desktop/dist`，但必须有可重复的打包/暂存步骤生成目标发布布局；不能只手工移动本机产物。
- 新发布包移除 `启动完整功能.cmd` 和旧名称的重复用户 EXE；开发测试宿主不视为用户入口，不应混入发布产物。
- 根目录、Python、前端、后端、runtime helper 的定位不依赖当前工作目录。中文、空格路径和从快捷方式启动均须可用。
- 当前代码从 `AppDomain.CurrentDomain.BaseDirectory` 向上两级找包根目录，移动后必须调整。
- 同一启动过程中，控制器 helper、业务后端和前端必须来自同一套经核验的安装目录，禁止当前包 EXE 搭配旧包 helper/页面而没有提示。
- 保留启动设置中的安装目录字段。首次可预填当前 EXE 所在的完整包目录；同包重开应恢复已保存有效值。发现保存值指向另一旧包时明确提示，不能悄悄继续使用旧包或删除旧目录。

### 3.2 默认模式与开发测试入口

- 不带参数启动即为正式完整模式：Python 自动检测/依赖准备和既有真实功能入口可用，端口继续自动管理。
- `--full-features` 如为兼容旧快捷方式而保留，应成为同一正式模式的兼容参数，不能再切换配置和单实例范围。
- 保留显式 `--test-profile` 等开发隔离能力；它们不能读写正式用户配置、业务数据或真实凭据。
- AI 服务首次使用默认启用；已有用户明确保存的启用/关闭选择应恢复，不能在每次 Main 启动时无条件覆盖。现有写入/提交确认规则不得放宽。
- 同一 Windows 用户的正式入口使用一致的单实例机制；不同启动目录或历史兼容参数不得再悄悄创建第二个正式实例。已有隔离测试实例保持隔离。
- 旧版本正在运行时，识别可确认的旧实例，提示先退出，不擅自杀进程或跨版本接管服务；不要将这种场景宣称为已完成升级。

### 3.3 统一启动设置与旧配置兼容

建议正式启动偏好固定到 `%LOCALAPPDATA%/VASP-Copilot/desktop/preferences.json`，不随版本号或入口参数变化。用一个明确初始化的配置存储实例/上下文供启动、设置表单、控制器共用，避免不同地方重复拼路径。

迁移规则：

1. 新目录已有有效正式配置时，以它为准；以后不再用旧目录覆盖。
2. 首次迁移只读取已知旧位置：`desktop-v040-full`、`desktop-v3`、`launcher`；不搜索用户全盘。
3. 只有一个有效旧来源，或多个有效来源内容一致时，可以一次性兼容导入；导入前保留旧文件，迁移成功后核验并记录来源。
4. 多个来源内容冲突时，一次性展示来源及安装目录/Python 等必要差异让用户选择；推荐原完整模式来源，但不能单凭修改时间强行覆盖。
5. 损坏、读不到的配置不可默认为“没有用户设置”。保留原件并说明问题，不静默写入空默认值。
6. 仅迁移启动偏好字段，延续明确的 `RootDirectory`、`PythonExecutable`、`EnableAi`、`VaspAiHome`、`DataDirectory` 语义。自动检测的 Python 输入留空表示用户选择自动模式，不能误报为保存丢失，也不能把应用专用 venv 当作用户手选基础解释器写回。
7. 本任务**不搬迁业务数据、项目数据库、凭据、浏览器数据或既有运行环境缓存**。特别注意：新偏好目录不能顺带让默认 home/data 变成空目录；旧来源中未显式保存的默认路径也要按原模式语义处理。无法无歧义判定时报告具体冲突，不猜测迁移。

### 3.4 保存/读取闭环与诊断

先核查实际保存链，再实施修复：设置表单接受新值 → 当前配置存储 → 写入目标文件 → 原子替换 → 重新读取 → 下一次进程加载。不得只改页面预填值来遮住保存缺陷。

必须达到：

- 明确显示/记录此次使用的配置来源与保存目标，便于区分不同入口、Windows 用户及旧实例。
- 每次保存使用所属操作的独立临时文件；并发防护与统一单实例配合，避免固定临时文件互相覆盖。
- 成功写入并核验关键字段后，才显示保存成功并继续启动。更改失败时不能让内存新值与磁盘旧值长期表现为“已保存”。
- 权限不足、文件占用、目录不可写、JSON 损坏、原子替换失败等给出可理解的错误和重试方式，保留旧有效配置，不写入空值覆盖。
- 读取时区分文件不存在、文件无效、访问失败；普通读取失败不能伪装成首次使用。重试须有界，不能无限等待或用延长 sleep 掩盖问题。
- 日志仅包含模式、版本、配置来源/目标、操作阶段、结果和异常类别等定位信息；不收集模型/MP 密钥、SSH 信息或整份业务配置。
- 为原故障提供最小只读诊断方式，能说明“实际运行的 EXE/版本/参数、读写哪个启动设置文件、上次保存在哪一步失败”。如无法取得另一台证据，回执明确说明，不宣称故障设备复测通过。

## 5. 执行顺序

1. **同步与复核**：检查工作区，保留既有修改；从总负责人确认的最新 main 新开独立分支，例如 `fix/dt01-desktop-entry-settings`。参考基线不代表必须回退到旧 SHA；记录实际基线。

3. **统一配置和入口语义**：先完成持久化、迁移与单实例，确保改变物理 EXE 位置前行为清楚。
4. **迁移发布布局**：根目录 EXE、相邻配置/依赖、资源定位、构建和校验链同步；删除多余用户入口。
