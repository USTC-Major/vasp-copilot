## 1. 用户要求与解释范围

用户提出：软件顶部五个按钮中的“工作流”可以删去，并将设置入口统一。2026-10-10 补充确认：统一范围包括原生桌面顶栏“启动设置”、网页右上角“智能设置”齿轮，以及网页左侧“执行设置”。

**以本次用户确认覆盖此前仅合并顶栏与齿轮的解释：三处设置统一收口，明确移除左侧“执行设置”导航项。** 桌面正常状态保留原生顶栏“设置”，隐藏网页重复齿轮；独立浏览器保留网页右上角“设置”。执行设置的功能纳入同一中心，不能随导航项一起删除。启动失败页仍保留恢复入口，后端配置存储职责保持不变。

目标是用户只需识别一个全局“设置”入口，进入后按用途找到本地运行与连接/计算设置。不能仅把两个按钮都改名为“设置”，也不能删除其中一个后丢掉其功能。

## 2. 已定位的代码与行为

### 2.1 桌面五按钮

`desktop/DesktopApp.cs` 的 `DesktopForm` 构造函数按以下顺序向 `bar` 添加控件：

| 现有按钮 | 当前行为 | 本任务目标 |
|---|---|---|
| 工作流 | 原生 WebView2 导航到 `/workflow` | 删除这一重复快捷按钮 |
| 启动设置 | `Configure()` 打开原生 `SettingsForm` | 改为统一“设置”入口，保留运行配置能力 |
| 关于 | 打开 `AboutForm` | 保留 |
| 重试启动 | 调用 `RunStartup()` | 保留原有行为 |
| 退出 | 关闭窗口并按既有流程清理所属服务 | 保留 |

隔离模式额外出现的“记录当前页面”是开发验收控件，不属于用户所说的五个正式按钮；本任务不把它加到正式界面。

`workflow` 不只出现在顶栏添加语句中，还参与健康状态恢复、启动/失败、导航完成时的 Enabled 赋值。删除时要清理这些引用，并保留 `evidence` 等其他控件原有状态控制，不能删除整段健康恢复逻辑。

### 2.2 网页设置与已有业务导航

- `frontend/src/components/workflow/ScientificWorkflowShell.tsx`：右上角齿轮 `aria-label="智能设置"` 跳转 `/ai/settings`；侧栏已存在“生成工作流”入口，因此删去原生快捷按钮不会移除工作流功能。
- `frontend/src/router.tsx`：`/ai/settings` 指向 `AiSettingsPage`；`/toolbox/settings` 指向 `ToolboxSettingsPage`。
- `frontend/src/pages/AiSettingsPage.tsx`：已有 LLM、SSH、Materials Project、作业执行/监控设置及保存、连接测试、未保存提示和凭据状态行为。
- `frontend/src/pages/ToolboxSettingsPage.tsx`：基础执行设置，AI 服务不可用时仍有独立用途；不能为合并入口而删掉这一能力。
- `desktop/DesktopApp.cs` 的 `BuildLaunch()`：启动/故障页另有“启动设置”恢复按钮；此处是无可用网页时的修复途径。

本轮源码核查未找到已建成的 WebView2 设置消息桥。不得假定前端已经能够读写桌面启动设置。

补充边界：`App.tsx` 还挂载聊天调用的 `LlmSettingsModal`。这不是本次右上角齿轮的实现，不得看到名称相似就顺手删除、复制或合并其模型配置接口；如实际接续时发现影响本次统一入口，先报告具体调用关系。

## 3. 目标交互

### 3.1 正常桌面状态

原生顶栏正式按钮收敛为：

```text
设置    关于    重试启动    退出
```

- 删除原生“工作流”按钮；工作流页面、侧栏入口、首次成功启动的默认页面保持现有行为。
- 原生“设置”打开统一设置中心；嵌入桌面时，网页右上角重复齿轮移除或不显示。
- 桌面和浏览器均移除侧栏“执行设置”入口，不再保留独立快捷入口。
- 设置中心按用途呈现三组能力：
  - **启动与运行**：安装目录、Python 自动检测/手动选择、智能模式服务开关、保存结果与运行诊断。以 DT-01 的配置与持久化实现为唯一来源。
  - **模型与材料**：LLM、Materials Project 配置及各自连接测试。
  - **超算与执行**：SSH、调度平台、最大作业数、监控轮询间隔及 SSH 连接测试。
  - 后两组复用已有业务表单、保存、测试与凭据状态逻辑，按分区整理展示，不建立重复配置。
- 这是统一入口和信息组织，不是把密钥写进桌面 `preferences.json`，也不是建立第三套设置。
- “关于”“重试启动”“退出”的行为不变；不要本轮重排主题、删除其他功能或更换 UI 框架。

### 3.2 网页独立运行

浏览器没有原生顶栏，必须保留一个网页“设置”入口并指向同一设置中心。不能为了桌面去重，在所有环境里一律隐藏齿轮。

仅桌面可用的“启动与运行”能力按环境显示可用状态；普通浏览器说明该项需在桌面程序操作，不伪造已保存状态、不尝试探测任意本机文件。已有 `/ai/settings`、`/toolbox/settings` 链接应继续可用，或兼容跳到设置中心的对应分区。

侧栏“执行设置”必须移除；其功能统一到“超算与执行”分区。旧 `/toolbox/settings` 地址与已有引用应兼容跳到该分区，不能留下独立设置页或失效链接；旧 `/ai/settings` 地址兼容进入同一中心。该变更只整理设置导航，不扩大为其他页面导航重构。AI 服务不可用时，“超算与执行”仍通过已有 Toolbox 接口读取、保存和测试基础执行配置。

### 3.3 启动失败与服务不可达

- Python 缺失、依赖安装失败、后端未启动、WebView2 不可用时，原生“设置”仍可打开本地启动配置。
- 启动/故障页的恢复按钮调用同一份原生配置逻辑。正常工作台只保留一个全局设置入口，不要求把故障处理按钮一并删除。
- AI 服务关闭或失联时，不能阻塞本地设置与基础 Toolbox 执行设置；保留已有不可用说明及重试路径。
- 不通过“先启动成功才能进入设置”的设计造成无法修复启动故障。

## 4. 推荐实施方式与边界

以“统一入口、分区展示、复用原有表单”为默认方案。可以新增一个轻量设置中心路由，由原生顶栏在服务就绪时调用前端导航，浏览器右上角入口打开同一中心；“启动与运行”通过受控的桌面动作复用原生 SettingsForm，不强求本轮把 Windows 文件选择和依赖安装全部重写为网页表单。运行不可用时直接回退到同一原生配置表单。

以下是实现约束，不要求为此引入通用桌面桥框架：

1. **避免整页重新导航丢草稿**：目前原生按钮使用 `CoreWebView2.Navigate`。新设置跳转应优先通过前端路由软切换或不会销毁当前工作台的承载方式实现；不能让打开设置再次触发工作流草稿全部丢失。正在编辑的设置离开前沿用未保存提示，不自动提交。
2. **只做必要的桌面通信**：若新增消息桥，仅允许少量固定动作，如打开设置中心、请求打开本地运行配置及查询桌面能力；校验消息结构、发送页的已核验本地来源和页面生命周期。不得接受任意 URL、任意路径写入、命令执行或直接返回密钥。
3. **有依据地区分桌面与浏览器**：不要只靠窗口宽度、URL 是 localhost、用户代理或随意可伪造的 localStorage 标记来开放原生权限；普通浏览器中没有桥时应正常降级。界面标记不能代替宿主侧校验。
4. **存储职责保持**：本地启动偏好归 DT-01；LLM/MP/SSH 凭据和业务设置继续走已有服务接口。不能复制密钥、另建配置文件，或为了统一界面改变清除/替换/测试已保存配置的语义。
5. **独立工作区和测试隔离保留**：设置操作不能改变当前项目、任务或业务数据归属。真正需要重启服务的本地设置变更应说明影响，沿用现有确认/执行流程，不暗中重启。

若为了实现统一中心需要改变服务接口、凭据边界或通用宿主权限，先向总负责人报告具体设计与文件范围；不要将其混入纯入口整理。DT-02 与 DT-01 改动同一桌面文件，禁止两个独立实现同时各改一套 Configure/保存流程。
