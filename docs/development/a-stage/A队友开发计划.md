## 3. A-1：诊断 LLM 接线

### 3.1 合同基准

现有 Toolbox 只读接口已经明确，可复用而不新增第三套 Toolbox 接口：

- `GET /api/v1/diagnosis/{diagnosis_id}`：取得结构化诊断结果；
- `GET /api/v1/diagnosis/{diagnosis_id}/report`：取得 Markdown 报告，未准备好时返回错误。

AI 侧目标接口：

- `GET /ai/v1/diagnosis/capabilities`
  - 返回 `mode: "ai"`、`enabled`、`configured`、`available`、`reason_code`；
  - `available` 只表示本地配置允许尝试调用，不表示模型已连通或回答质量已验证；
  - 不 ping 模型或 SSH，不返回密钥或掩码。
- `POST /ai/v1/diagnosis/explain`
  - 请求严格为 `{diagnosis_id, question}`，拒绝额外字段；
  - `diagnosis_id` 非空且不得包含路径分隔符；
  - `question` 去首尾空白后限制为 1～4000 字符；
  - 成功返回 `{mode: "ai", ok: true, diagnosis_id, answer, evidence_source: "toolbox_diagnosis", context_truncated}`；
  - 失败沿用 AI 的 `{mode, error: {code, message, retryable}}` 结构和非 2xx 状态。

### 3.2 实现步骤

1. **代码盘点**
   - 找到智能模式已有设置读取、开关、LLM provider 工厂和错误处理入口；
   - 找到诊断结果页现有“LLM 未启用”提示、旧配置弹窗和旧 explain 调用；
   - 核对现有 `ToolboxClient` 的基址和路径前缀，不能用 `../diagnosis` 绕过客户端能力。
2. **AI 只读适配器**
   - 使用服务配置的 `TOOLBOX_URL`；
   - 对 `diagnosis_id` 做单路径段编码和校验；
   - 不接受用户 URL、文件路径或重定向转发凭据；
   - 只读取结构化诊断证据，必要时再读取报告，不重新运行诊断。
3. **能力状态路由与前端状态**
   - 状态读取与实际 explain 请求使用同一配置来源；
   - 明确区分加载中、未配置、主动关闭、AI 服务不可达、状态读取失败、模型调用失败和可使用；
   - 停用、清除或替换配置后使前端缓存失效；
   - 旧配置只保留兼容入口，不偷偷回退旧明文配置。
4. **解释路由**
   - 每次请求读取当前配置；
   - 只解释，不调用 agent 执行器、工具卡或修复应用；
   - 成功回答必须非空，前端只有 `ok=true` 才显示为回答；
   - 将诊断证据投影为白名单字段，排除完整原始日志、上传内容、本地路径、密钥、旧 LLM 明文和整套 plot 数组；
   - 按确定顺序裁剪输入，初始上限 24,000 字符或受模型上下文限制的较小值，裁剪时显式标记。
5. **诊断页接入**
   - 前端只发送 `diagnosis_id` 和问题；
   - AI 缺席或失败时保留原报告、图表和人工修复信息；
   - 错误提供“重试／去设置／先运行诊断”等正确下一步，不把错误字符串包装成成功回答；
   - 不顺便重构诊断图表或修复卡。

### 3.3 A-1 验证

- 单元/接口测试：合法请求、额外字段、空 ID、路径分隔符、问题长度边界、空回答；
- 状态测试：未配置、关闭、Fake provider、服务不可达、诊断不存在、诊断未完成、无效响应、超时、模型失败；
- 配置生命周期：保存、替换、清除、停用后缓存失效且不回退旧密钥；
- 受控 Toolbox 响应测试：结构化结果、缺字段、裁剪标志、诊断报告未准备好；
- 前端测试：AI 失败时原报告仍可见，成功解释与 `diagnosis_id` 绑定；
- 按项目要求运行相关测试、`frontend npm run build` 和 `frontend npm run lint`；
- 不声称真实模型质量或真实 Toolbox/计算验证通过。

## 5. A-3：设置页面结构与行为

### 5.1 页面分区

设置页固定分为：

1. LLM；
2. SSH；
3. Materials Project；
4. 作业执行／监控。

三个连接测试必须位于各自配置模块内，结果也显示在对应模块中并保持可见。

### 5.2 行为合同

- 测试按钮明确表示测试的是已保存配置；
- 表单有未保存修改时，测试操作提示先保存；
- 不因测试而悄悄保存，也不自动发起测试；
- 保存、替换、清除凭据的既有语义保持不变；
- 保留配置冲突保护；
- 测试结果不能只通过短暂全局 toast 展示；
- B-2 只补 label/help/单位/可访问标签，不重复修改以下逻辑。

### 5.3 数值输入与校验

- `max_jobs` 为整数，最小值 1；
- `poll_interval_seconds` 为整数，范围 10～3600 秒，默认 60 秒；
- 空白不是 0；
- 空值、非法数值和越界值要有明确错误；
- 默认值展示不得覆盖用户已有保存值；
- 保持现有表单序列化合同，若使用 `InputNumber` 不能改变提交字段形状。

### 5.4 实现步骤

1. 盘点 `AiSettingsPage`、保存转换、凭据处理、冲突检查、测试请求和现有测试。
2. 先建立四块页面结构，再把三个测试按钮和结果状态放回所属模块。
3. 添加“已保存配置”语义和未保存检测，确保测试前不会隐式提交。
4. 将结果状态放在对应模块的持久区域，覆盖成功、失败、连接不可达和需要保存等状态。
5. 一次实现整数/范围/空值校验，并为保存和测试路径补回归测试。
6. 不整体替换设置页，不改变 `toForm`、`patchFields`、`onSubmit`、SecretInput、useEffect 和后端 API 合同，除非发现合同缺口并先报告。
7. 完成后向 B 提供该页交付基线、修改文件、测试结果和明确的 B-2 起始点。

### 5.5 A-3 验证

- 四个模块在桌面和窄窗口下顺序清晰；
- 每个测试按钮只测试已保存配置；
- 修改字段但未保存时测试被阻止并给出明确提示；
- 保存后测试使用新配置；清除/替换凭据不回退旧值；
- 测试结果在对应模块持续可见；
- `max_jobs=0`、负数、小数、空值和合法值分别覆盖；

## 6. A-4：计算任务模块新手指引

### 6.1 启动条件

只有 B-1 已完成并集成到最新 `main` 后开始。开始前确认任务页仍使用 B-1 的展示改动，导入、查询、缓存和请求身份仍保留 raw MP ID。

### 6.2 页面内引导内容

引导应简短、可按当前状态理解，至少回答：

- 这个页面管理项目任务、输入文件、作业计划、远端准备、提交和结果获取；
- 只有结构时：先登记/扫描输入，再按当前支持的计划和生成流程准备文件；
- 已有输入文件时：从登记/扫描已有输入开始，不重复生成已有文件；
- 计划：描述要做的作业，不等于已生成输入或已提交；
- 生成：生成受支持的输入/草稿，不等于已登记、已上传或已提交；
- 登记：让 Toolbox 建立可追溯的输入元数据；
- 上传：把经过确认的文件传到远端，不等于作业已经提交；
- 提交：经过预检、草稿和人工确认后请求调度，不等于结果已产生；
- 结果获取：终态后按准确任务和 attempt 获取结果；
- 当前状态下的下一步：根据实际状态显示待登记、待补文件、待确认、待预检、待提交、监控或取结果等提示。

### 6.3 中文指南更新

复用现有中文使用指南和 Toolbox 的真实操作事实，保持与页面术语一致。明确写出：

- 保存计划不等于提交；
- 生成脚本不等于执行脚本；
- 上传和提交分别需要什么条件；
- 结果获取的任务/作业身份要求；
- 待确认、失败、unknown 和未完成状态的下一步；
- AI 是可选解释能力，AI 失败不影响确定性报告。

不加入未实现流程模板、自动提交、自动纠错、连续执行或目录初始化。

### 6.4 A-4 验证

- 通过合成或获准样例检查“只有结构”和“已有输入”两条路径；
- 检查计划、生成、登记、上传、提交、结果获取的文案不互相混淆；
- 检查不同任务状态下下一步提示不越权、不声称已经执行；
- 检查 B-1 的数字 MP ID 展示和原始 ID 可查行为未被破坏；
- 窄窗口下引导可读，不遮挡任务操作区；
- 由总负责人核对 Toolbox 操作事实；
- 页面稳定后再补截图；未做截图或真实计算时明确记录为未验证。

## 7. 统一测试、交付与回执

### 7.1 测试原则

- 优先运行任务相关测试，不为凑数量重复跑相同套件；
- 使用项目既有测试隔离、合成数据和受控响应；
- 不复制个人 `.env`、密钥、用户数据或私有计算文件；
- 不把 FakeLLM、模拟 HTTP 或静态构造当成真实模型、SSH、HPC 或 VASP 验证；
- 最终 PR 前执行相关测试、前端 `npm run build` 和 `npm run lint`；
- 浏览器检查需记录实际检查内容和未检查内容。

### 7.2 每项交付回执

```text
任务号：
基线 SHA / 交付 SHA 或差异：
```

### 7.3 集成原则

- 每项由唯一主责交付，总负责人审核和集成；
- 不因单项测试通过而宣称 A 批全部完成；
- A-1 与总负责人的诊断数据/结果页变更按接线窗口串行集成；
- A-3 合入后再交 B-2；B-1 合入后再接 A-4；
- 集成后由总负责人统一复检原流程、A 批新行为、AI 可选性、失败恢复和原有修改保护；
- 未完成真实科学/外部服务验证时，在最终回执中明确列为待验。

- 没有自动合并、发布、真实计算或未经授权的外部服务调用。
